# OS v0.2.1 -> v1.0.0 Roadmap

## Executive Summary
PrismOS v0.2.1 is a bootable 32-bit x86 hobby OS with a working interrupt pipeline, framebuffer console, keyboard input, PIO IDE block device, FAT32-backed VFS, shell, and a substantial in-kernel app/toolchain stack (BCVM runtime, editor, IDE, and subset-C compiler).

The strongest reality-based conclusion is this:
- Kernel core is still early-stage and single-address-space.
- App/tooling layer is already advanced and large.
- The biggest risk is architectural inversion: complex application features are running on top of a still-minimal kernel foundation.

A credible v1.0.0 is achievable without building a full Unix-like OS, but it requires first stabilizing core kernel contracts (memory, fault handling, timing, execution model, and testability), then hardening storage/app execution paths.

## Current Architecture
### Boot process and bootloader
- GRUB multiboot2 is used via [boot/grub.cfg](boot/grub.cfg).
- Kernel entry is assembly start in [boot/boot.s](boot/boot.s), storing multiboot magic/info and calling C main.
- Multiboot2 framebuffer tag parsing happens in [src/kernel.c](src/kernel.c).
- Link layout is in [boot/linker.ld](boot/linker.ld): sections are linked with text/data/bss starting at 1 MiB.

Status:
- Implemented and working for BIOS/GRUB-based x86 boot flow in QEMU.
- No UEFI-native loader in repo.

### CPU architecture
- Build flags and assembly indicate 32-bit IA-32 protected mode (gcc -m32) in [Makefile](Makefile).
- QEMU runner is x86_64 machine emulating a BIOS guest, but kernel binary is 32-bit.

Status:
- Implemented: x86 32-bit only.
- Missing: x86_64 long mode path, ARM, RISC-V.

### Kernel entry and init order
Main startup sequence in [src/kernel.c](src/kernel.c):
1. Validate multiboot magic.
2. Parse framebuffer tag.
3. Initialize PSF font and console.
4. Initialize PMM and paging.
5. Bring up interrupts (GDT, PIC remap, IDT, IRQ table, sti).
6. Initialize keyboard and COM IRQ.
7. Initialize block device and mount VFS.
8. Initialize app manager.
9. Enter shell loop forever.

Status:
- Implemented and coherent for a monolithic boot-to-shell flow.

### Kernel architecture style
- Monolithic, single-address-space kernel.
- No process abstraction; apps and tools execute in kernel context via direct function dispatch (not ring transitions).

Status:
- Implemented: monolithic kernel + in-kernel apps.
- Missing: privilege boundary, process isolation, scheduler.

### Memory layout and PMM
- PMM in [src/memory/pmm.c](src/memory/pmm.c) uses a global bitmap over 4 GiB addressable space.
- Frees only multiboot-usable regions; reserves low 1 MiB, kernel range, multiboot info region, framebuffer.
- Exposes page allocation/free APIs.

Status:
- Implemented: basic physical page management.
- Partially implemented: no ownership tracking, no poisoning, no stats validation tooling.

### Virtual memory and paging
- Paging in [src/memory/paging.c](src/memory/paging.c): 4 KiB pages, static page directory and static page-table pool.
- Identity maps 0..64 MiB plus kernel and framebuffer.
- Page fault vector handler exists but only halts.

Status:
- Implemented: bootstrap paging enablement.
- Partially implemented: map/unmap primitives exist, but no dynamic PT allocation from PMM and no address-space abstraction.
- Fragile: static BOOTSTRAP_PT_COUNT limits scale.

### Heap allocator
- No kernel heap allocator present (no kmalloc/kfree/slab/buddy interfaces found).

Status:
- Missing.

### Interrupts and exceptions
- GDT setup in [src/platform/gdt.c](src/platform/gdt.c): flat ring0 code/data.
- IDT setup in [src/interrupts/idt.c](src/interrupts/idt.c) with vectors for exceptions 0-31 and IRQs 32-47.
- ISR/IRQ stubs in [src/interrupts/isr_stubs.s](src/interrupts/isr_stubs.s).
- PIC remap/mask/unmask/EOI in [src/platform/pic.c](src/platform/pic.c).
- Generic dispatch in [src/interrupts/irq.c](src/interrupts/irq.c).

Status:
- Implemented: hardware interrupt plumbing for legacy PIC.
- Partially implemented: exception hooks exist, default behavior is panic halt.
- Missing: timer IRQ policy, deferred work, APIC/IOAPIC.

### Drivers and hardware abstraction
- Keyboard PS/2 IRQ1 driver in [src/input/keyboard.c](src/input/keyboard.c).
- COM1 driver and IRQ4 RX buffering in [src/comport/comport.c](src/comport/comport.c).
- Separate serial helper in [src/display/serial.c](src/display/serial.c).
- ATA PIO primary master block device in [src/filesystem/blockdev.c](src/filesystem/blockdev.c).

Status:
- Implemented: minimal but real hardware-facing drivers.
- Missing: PCI bus enumeration, USB stack, network stack, audio, graphics acceleration.

### Display/framebuffer/VGA
- Framebuffer text console with PSF glyph rendering in [src/display/console.c](src/display/console.c) and [src/display/psf_font.c](src/display/psf_font.c).
- Color palette and pixel draw primitive are implemented.

Status:
- Implemented: functional text UI over framebuffer.
- Partially implemented: cursor blink support exists via console_tick but appears unconnected to timer path.

### Storage and filesystem
- Raw ATA PIO sector read/write, identify, and blank-disk FAT bootstrap in [src/filesystem/blockdev.c](src/filesystem/blockdev.c).
- FAT32 mount/list/read/write/mkdir/rm/rmdir/path checks in [src/filesystem/fat32/fat32.c](src/filesystem/fat32/fat32.c).
- VFS normalization and adapter layer in [src/filesystem/vfs.c](src/filesystem/vfs.c).

Status:
- Implemented: persistent storage against QEMU disk image.
- Partially implemented: simplified FAT32 (8.3 names, narrow geometry assumptions, no journaling, no LFN).

### PCI/USB/networking/timers/RTC/SMP
- No implementation files for PCI, USB, network, timers, RTC, APIC, SMP.
- IRQ stubs include timer/RTC vectors but no timer/RTC driver registration is present.

Status:
- Missing.

### Processes, threads, scheduling, syscalls, user/kernel split
- No scheduler, process table, context switch, syscall ABI, TSS/user segments, or ring3 execution path.

Status:
- Missing.

### Executable loading and userspace programs

- Runtime dispatch in [src/apps/app_runtime.c](src/apps/app_runtime.c).

Status:
- Implemented: app package loading and bytecode execution.

### Shell and command system
- Shell input/edit/history loop in [src/shell/shell.c](src/shell/shell.c).
- Command registry and handlers in [src/commands/command.c](src/commands/command.c).

Status:

### IPC and synchronization primitives
- No IPC subsystem (pipes, message queues, shared memory channels).
- Ring buffer utility in [src/util/ringbuf.c](src/util/ringbuf.c) used for interrupt-driven byte/event buffering.

Status:
- IPC missing.

### Security/isolation

- Banking app stores plaintext credentials in filesystem in [src/apps/bank_app.c](src/apps/bank_app.c).

### Build system/toolchain

### Testing/debugging/logging/docs/config/release process

## v0.2.1 Current State
### What the OS can currently boot on
- Confirmed path: GRUB multiboot2 BIOS in QEMU with framebuffer.
- Real bare-metal coverage: UNKNOWN — requires verification.

### What happens after boot
- Kernel enters shell after init and offers filesystem/app commands.
- If framebuffer tag is missing, kernel switches to serial diagnostics and halts.

### What users can currently do
- Use interactive shell: help, clear, echo, about, reboot/shutdown, ls/cd/touch/mkdir/rm/rmdir/delete/cat/write/append/mv, edit, ide, app-run, cc.
- Edit files, compile subset-C apps, run bytecode apps, run banking app.

### Hardware support snapshot
- Keyboard PS/2, COM1, framebuffer, ATA PIO primary disk.
- No PCI discovery, no USB, no networking, no SMP.

### Kernel/userspace boundary
- Not present. All app and compiler logic runs in kernel address space.

### Multitasking
- No process/thread scheduler; single blocking execution flow.

### Memory protection
- Paging enabled, but no user/kernel page permission model or per-task page tables.

### Persistent storage
- Yes, via FAT32 on raw disk image sectors.

### Program loading/execution
- Yes, through Prism app packages and BCVM/native built-in app IDs.

### Shell usability
- Usable for single-user interactive operation with command history and inline editing.

### Stability assessment
- Good for demo-level flows in emulator.
- Medium risk under malformed app inputs, compiler edge cases, and missing recovery paths.

### Biggest technical limitations
- No execution isolation or preemptive scheduling.
- No timer subsystem to drive periodic services.
- No kernel heap allocator.
- Exception and page fault handling mostly fatal.
- Driver model does not yet scale beyond hardcoded devices.

## Architectural Problems
### 1) Architectural inversion: app/toolchain complexity exceeds kernel foundations
Problem:
- Large in-kernel compiler and VM stack ([src/apps/prismcc_runtime.c](src/apps/prismcc_runtime.c), [src/apps/bytecode_vm.c](src/apps/bytecode_vm.c)) rides on kernel lacking scheduler/isolation/heap.

Why it matters:
- Kernel crashes or corruption in app paths become likely blockers for all future work.

What breaks if ignored:
- Every new language/runtime feature amplifies kernel risk and debugging cost.

Recommended solution:
- Freeze language-surface growth, prioritize kernel core hardening milestones first.

Milestone:
- Phase 0 and Phase 1.

### 2) No timer subsystem
Problem:
- No PIT/RTC/APIC timer driver active despite IRQ stubs.

Why it matters:
- No preemption, no tick-driven services, no reliable timeouts.

What breaks if ignored:
- Scheduler cannot be introduced cleanly; IO and UI remain fully blocking.

Recommended solution:
- Add PIT tick source first, then abstract timer API.

Milestone:
- Phase 1.

### 3) No kernel heap allocator
Problem:
- Dynamic subsystem growth is constrained; static arrays dominate large modules.

Why it matters:
- Limits extensibility and can force unsafe static/global patterns.

What breaks if ignored:
- Driver expansion, buffered IO, process/task objects become brittle.

Recommended solution:
- Implement kmalloc/kfree atop PMM + paging, with simple slab or segregated freelists.

Milestone:
- Phase 2.

### 4) Paging architecture capped by static table pool
Problem:
- Static BOOTSTRAP_PT_COUNT in [src/memory/paging.c](src/memory/paging.c).

Why it matters:
- Virtual memory growth and per-address-space plans cannot scale.

What breaks if ignored:
- Later process isolation and memory mapping features hit hard limits.

Recommended solution:
- Allocate page tables from PMM dynamically and track ownership.

Milestone:
- Phase 2.

### 5) Fatal exception policy and limited fault diagnostics
Problem:
- Default unhandled exception handling panics/hlt.

Why it matters:
- Debugging and survivability are poor.

What breaks if ignored:
- Recoverable faults and user-facing reliability cannot improve.

Recommended solution:
- Install per-vector policy handlers, classify fatal vs recoverable, preserve diagnostics.

Milestone:
- Phase 1.

### 6) Block device/filesystem assumptions are narrow
Problem:
- ATA PIO only, single-disk assumptions, simplified FAT32 geometry in formatter path.

Why it matters:
- Portability and robustness are limited.

What breaks if ignored:
- Storage bugs under non-default disk layouts or future multi-device needs.

Recommended solution:
- Separate disk discovery, partition awareness (or explicit superfloppy policy), and FAT32 driver contracts.

Milestone:
- Phase 4.

### 7) Versioning/documentation drift
Problem:
- About command reports old version.

Why it matters:
- Inconsistent releases and support confusion.

What breaks if ignored:
- Reproducibility and test matrix trust decline.

Recommended solution:
- Single source of truth for version metadata propagated into shell/docs/build artifacts.

Milestone:
- Phase 0.

## v1.0.0 Definition
A realistic v1.0.0 for this project should mean:
- Stable single-user OS environment in emulator and selected hardware targets.
- Reliable shell + persistent filesystem + app package execution.
- Hardened kernel internals with deterministic fault handling and regression tests.
- Optional ring3 isolation can remain post-1.0 if VM sandbox hardening is explicit and documented.

### MUST HAVE
- Deterministic boot and init diagnostics.
Reason: Required for every support and release workflow.

- Stable interrupt and timer infrastructure (PIT-based tick minimum).
Reason: Needed for responsiveness, timeouts, and future scheduling.

- PMM + paging + kernel heap baseline.
Reason: Required to scale kernel data structures safely.

- Robust FAT32 and block IO behavior for normal shell/app operations.
Reason: Persistent workflow is central to PrismOS identity.

- Hardened BCVM execution guardrails and clear resource limits.
Reason: Current app ecosystem depends on VM heavily.

- Unified error model and non-catastrophic handling where practical.
Reason: Prevent trivial faults from halting system.

- Automated regression tests for boot, memory primitives, fs, and app runtime.
Reason: v1.0 credibility requires repeatable quality gates.

- Versioned release process with changelog and RC criteria.
Reason: Required for a stable release claim.

### SHOULD HAVE
- Basic cooperative task framework (even before full preemption).
Reason: Reduces global blocking and prepares for scheduler.

- Early syscall abstraction layer (internal first).
Reason: Enables future user/kernel boundary without rewiring all APIs.

- Partition-awareness or explicit superfloppy contract in storage docs/code.
Reason: Avoid silent data layout assumptions.

- Security improvements for app data handling (at least no plaintext credentials for demo apps).
Reason: Improves trust and reduces harmful defaults.

### NICE TO HAVE
- Ring3 userspace with true process isolation.
Reason: Important long-term, but large scope jump from current baseline.

- PCI/USB/network stack.
Reason: Not necessary for first credible stable milestone given project scope.

- SMP and APIC migration.
Reason: Valuable future scalability target, not required for first stable.

## Critical Dependencies
Dependency chain derived from current codebase reality:

Bootloader + multiboot contract
-> Early console and logging
-> GDT/IDT/PIC/IRQ pipeline
-> PMM initialization from multiboot memory map
-> Paging enablement and page fault path
-> Kernel heap allocator
-> Timer subsystem
-> Task execution model (cooperative then preemptive optional)
-> Storage abstraction hardening
-> FAT32/VFS reliability and limits tests
-> App manager/runtime hardening
-> Automated tests + release pipeline
-> v1.0.0

Critical path items:
- Timer and heap are hard blockers for scheduler-quality improvements.
- Memory + fault handling hardening are blockers for safe app/runtime growth.
- Test infrastructure is a blocker for stable release confidence.

# OS v0.2.1 → v1.0.0 Roadmap

## Executive Summary
PrismOS v0.2.1 is a bootable 32-bit x86 hobby OS with a working framebuffer console shell, interrupt setup, keyboard input, ATA PIO disk I/O, a writable FAT32-like filesystem layer, and an unexpectedly advanced in-kernel app platform (BCVM runtime, in-OS subset C compiler, editor, IDE, banking app).

The kernel foundation is functional but architecturally shallow: single address space, no scheduler, no processes/threads, no timer subsystem, no syscall ABI, no ring3 boundary, and panic-oriented fault handling. The biggest strategic risk is that user-facing app features are outpacing kernel safety and isolation.

The shortest technically sound path to a credible v1.0.0 is:
1. Stabilize kernel correctness and observability.
2. Add timebase plus basic tasking model.
3. Harden storage/filesystem semantics.
4. Refactor app runtime boundaries and error model.
5. Introduce minimal privilege separation and syscall surface (even if BCVM remains primary app model).
6. Freeze interfaces, run regression matrix, ship.

## Current Architecture
Boot and early init path observed from source:
1. GRUB multiboot2 loads kernel ELF with framebuffer request in [boot/boot.s](boot/boot.s).
2. Entry symbol start stores multiboot registers, sets stack, calls C main in [boot/boot.s](boot/boot.s).
3. Link layout is low memory with sections defined in [boot/linker.ld](boot/linker.ld).
4. Kernel main validates multiboot magic, parses framebuffer tag, initializes console, PMM, paging, interrupts, keyboard, COM IRQ, disk, VFS, app manager, then enters shell in [src/kernel.c](src/kernel.c).

Platform assumptions:
- ISA: IA-32 protected mode, ring0-only flat segmentation via [src/platform/gdt.c](src/platform/gdt.c).
- Boot mode: BIOS/GRUB multiboot2, not UEFI-native loader.
- Interrupt controller: 8259 PIC via [src/platform/pic.c](src/platform/pic.c), no APIC/IOAPIC.
- Storage path: ATA primary bus PIO (LBA28-oriented path, light identify probing) in [src/filesystem/blockdev.c](src/filesystem/blockdev.c).

Execution model:
- Single kernel control flow.
- No process scheduler.
- No user mode transitions.
- Apps run in kernel context through dispatch and BCVM interpreter in [src/apps/app_runtime.c](src/apps/app_runtime.c) and [src/apps/bytecode_vm.c](src/apps/bytecode_vm.c).

## Architectural Problems

1. Problem: App and compiler execution in ring0 kernel context.
- Why it matters: Any parser/runtime bug can corrupt kernel state.
- What breaks if ignored: Stability, security, and deterministic debugging collapse as feature complexity grows.
- Recommended solution: Introduce minimal process boundary and syscall ABI; in interim isolate runtime via strict capability layer.
- Milestone: Phase 4 starts boundary hardening, Phase 5 completes ring3/syscall path.

2. Problem: No timer subsystem or scheduler.
- Why it matters: Cannot support background tasks, timeouts, fair input processing, or future multi-program runtime.
- What breaks if ignored: UI stalls, no responsive multitask growth path.
- Recommended solution: Implement PIT driver, monotonic tick source, and simple scheduler.
- Milestone: Phase 2.

3. Problem: No kernel heap allocator.
- Why it matters: Static buffers drive hard limits and brittle features.
- What breaks if ignored: Growth of FS/apps/driver buffers causes fragmentation of design and unsafe fixed-cap hacks.
- Recommended solution: Add kmalloc/kfree on top of PMM + paging-backed virtual heap region.
- Milestone: Phase 1.

4. Problem: Paging design is bootstrap-only (identity map + static PT pool).
- Why it matters: No scalable VM for processes, copy-on-write, guard pages, or kernel/user split.
- What breaks if ignored: Ring3 introduction becomes near-rewrite.
- Recommended solution: Introduce page-table allocator and address-space abstractions.
- Milestone: Phase 1 foundational refactor.

5. Problem: Exception handling policy is panic-centric.
- Why it matters: Recoverable faults are treated as fatal.
- What breaks if ignored: Poor debuggability and no fault containment for user tasks.
- Recommended solution: Structured exception paths, panic reason codes, optional kill-current-task model.
- Milestone: Phase 1 then Phase 5.

6. Problem: Filesystem consistency model is weak.
- Why it matters: Power loss or interrupted updates can leave corruption.
- What breaks if ignored: Data loss and unreliable app workflow.
- Recommended solution: Write ordering discipline, atomic update patterns, fsck-lite checks at mount.
- Milestone: Phase 3.

7. Problem: Build uses host gcc toolchain with weak reproducibility and linker warnings (RWX segment, executable stack note).
- Why it matters: Security posture and reproducibility concerns.
- What breaks if ignored: Non-deterministic builds across hosts; difficult release confidence.
- Recommended solution: Pin cross-toolchain, tighten linker flags, mark non-exec stack where possible.
- Milestone: Phase 0.

8. Problem: Documentation and runtime metadata drift (version mismatch, feature drift).
- Why it matters: Operators and contributors cannot trust reported state.
- What breaks if ignored: Release process errors and debugging confusion.
- Recommended solution: Single source version constant + release checklist.
- Milestone: Phase 0.

## v1.0.0 Definition
A realistic v1.0.0 for this project is not full desktop OS parity. It is a stable, test-backed, single-user development OS with persistent storage and protected app execution boundaries sufficient to prevent routine app failures from taking down the kernel.

### MUST HAVE
1. Deterministic boot in QEMU and documented hardware subset.
Reason: Baseline release credibility.

2. Stable kernel init, PMM, paging refactor with dynamic page-table allocation and kernel heap.
Reason: Required for continued growth and memory safety.

3. Timer + scheduler baseline (at least kernel task scheduling with preemption or cooperative plus time slicing).
Reason: Required for responsiveness and future user tasks.

4. Minimal syscall ABI and ring3 execution for at least one user task type, or equivalent hard isolation mechanism.
Reason: Must close ring0 app-execution risk before 1.0.

5. Persistent filesystem with mount checks and regression-tested file operations.
Reason: PrismOS value proposition includes in-OS editing and compilation.

6. Shell and app workflow remain functional: edit, compile, run, manage files.
Reason: Core user experience continuity.

7. Structured logging + panic diagnostics + automated regression suite in emulator.
Reason: Required for maintainability and release confidence.

### SHOULD HAVE
1. Native executable loader for a tiny user binary format.
Reason: Enables growth beyond BCVM and validates syscall model.

2. Better device abstraction and early PCI enumeration.
Reason: Prepares driver scalability but can trail core stability.

3. Basic permission model or capability scoping for filesystem/app APIs.
Reason: Security improvement without blocking first stable release.

4. In-kernel compiler hardening and resource limits.
Reason: Important due attack surface, but can be incrementally improved.

### NICE TO HAVE
1. Networking stack.
Reason: Large scope; not required for credible 1.0 in current trajectory.

2. USB support.
Reason: Significant complexity beyond current device model.

3. SMP support.
Reason: Not needed for first stable single-core release.

4. GUI/windowing.
Reason: Out of scope relative to kernel fundamentals.

## Post-v1.0.0 Suggestions
1. PCI-based driver discovery and modular driver loading.
2. Networking MVP (NIC driver + minimal IP stack).
3. USB keyboard/storage support.
4. SMP bring-up and scheduler scaling.
5. Optional native executable toolchain beyond BCVM.

## Biggest Risks
1. Privilege separation effort may reveal deep assumptions in current app/runtime design.
2. Scheduler introduction can expose race conditions in existing drivers.
3. Filesystem hardening can break compatibility with existing disk images.
4. Large monolithic compiler/runtime files increase regression risk during refactor.
5. Limited automated tests can mask subtle memory bugs until late RC stages.

## Recommended Development Order
1. Phase 0 stabilization and observability.
2. Phase 1 memory and VM foundations.
3. Phase 2 timer and scheduling.
4. Phase 3 filesystem reliability.
5. Phase 4 app platform hardening.
6. Phase 5 ring3 and syscall boundary.
7. Phase 6 RC hardening and freeze.
8. Phase 7 v1.0.0 release.

Single recommended critical path:
Boot stabilization → memory and heap refactor → timer and scheduler → syscall and user isolation baseline → filesystem reliability gates → app runtime hardening under capability policy → full regression automation → v1.0.0 release.

## Final Assessment
PrismOS v0.2.1 is a strong prototype with unusually ambitious developer-facing app features for its kernel maturity level. The project is credible and already useful as an experimental environment, but it is not yet architecturally safe for a stable 1.0 release because isolation, scheduling, and test discipline lag behind feature complexity.

If the roadmap above is followed in dependency order, v1.0.0 can be both realistic and defensible for a small independent OS project.
